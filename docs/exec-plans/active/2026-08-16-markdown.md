# Exec Plan: Markdown in the thread column (I)

No separate spec. The decisions were settled from a live mockup on 2026-08-16
and are recorded here; the mockup is the visual reference.

Status legend: `todo` · `in-progress` · `done`.

Written against the tree at `0941e4b`. Verify a named symbol still says what a
ticket claims before editing it.

## The problem

`markdown.ts` reads three things: paragraphs, lists, fenced code. Everything
else an agent writes reaches the reader as raw punctuation — `## Usage`, `---`,
`**bold**` all render literally. Ordered lists restart at 1 whenever a nested
bullet interrupts them. And a fenced block sits inside its message, so `j`
steps over a whole answer at once instead of stopping at the code.

## Decisions

1. **A heading never changes the type size.** Every heading renders at body
   size. Depth is carried by weight, colour, and a hairline — never by scale.
2. **Variant A, "Rule".** A heading is bold at body size with a hairline
   running out to the column edge. A level-three heading gets a lighter weight
   and a fainter line. This is the language the statusbar, the ledger spine and
   the old checkpoint rule already speak.
3. **A fenced block is its own nav block.** `text · code · text` is three stops
   for `j`. It is done the way the ledger already does it — one model block,
   several nav entries — not by splitting the block in the reducer, where a
   fence opening mid-stream would have to be handled twice.
4. **Syntax highlighting is per line, with a carry state.** Each line is
   tokenised from the state the previous line ended in.

   The carry is `inBlockComment` and nothing else. A string that never closes
   ends at its line, which is what every editor does and what keeps one stray
   quote from dyeing the rest of a block; the cost is that a multi-line
   template literal or a Python triple-quote mis-colours its continuation
   lines. Accepted.

   The renderer re-tokenises the whole block per streamed token, not just the
   last line. The per-line API supports the incremental shape and the block is
   re-parsed per token anyway, so the caching was not worth its own state;
   revisit if a long block ever shows up in a frame trace.
5. **Tables are out of scope**, by explicit decision. `| a | b |` keeps
   rendering as text for now. When it is picked up, the open question is
   whether a table also becomes its own nav block, as code now does.
6. **Emphasis covers `**bold**` only.** Italic is adjacent and cheap, but it
   was not asked for, and `*` is common in agent prose about globs and
   multiplication. Left alone deliberately.

## I1 — the document renders as a document — `done`

Delivered behavior: an agent message shows headings, thematic breaks and bold
text instead of raw punctuation, and an ordered list interrupted by a nested
bullet keeps counting.

Steps:

1. `src/renderer/src/lib/markdown.ts` — extend `MarkdownNode`:
   - `| { type: 'heading'; level: 1 | 2 | 3; segments: InlineSegment[] }`
   - `| { type: 'rule' }`
   - Extend `InlineSegment` with `bold?: boolean`. Keep `code` as it is; the
     two are independent, so `**`code`**` stays possible.
2. Same file, `parseMarkdown`:
   - `const HEADING = /^(#{1,6})\s+(.*)$/` — clamp `level` to 3, because the
     rendering has three treatments and a `####` that silently rendered as
     body text would be worse than one that renders as a level three.
   - `const RULE = /^\s*(-{3,}|\*{3,}|_{3,})\s*$/` — checked **before** the
     bullet rule, or `---` parses as a list item.
   - Both flush the open paragraph and list first.
3. Same file, list nesting — this is the ordered-list bug:
   - `BULLET` and `NUMBERED` already capture the text but throw away the
     indent. Capture it: `/^(\s*)[-*]\s+(.*)$/`.
   - Give a list item children: `{ segments: InlineSegment[]; children?: ListNode }`.
   - An item indented further than the item above it becomes that item's
     child list rather than closing the parent. One level of nesting is
     enough; a deeper indent joins the level above it rather than growing a
     third, the same limit the ledger puts on subagent rows.
4. Same file, `parseInline` — read `**` as well as backticks. A single state
   machine over both markers, not two passes: `**a `b` c**` must come out as
   one bold run containing a code segment.
5. `src/renderer/src/components/thread/Message.svelte`:
   - Render `heading` as `<div class="h h{level}">`, and `rule` as
     `<div class="rule" role="separator">`.
   - Heading CSS, Variant A: `font-size: inherit`, `font-weight: 700`,
     `color: var(--fg-bright)`, `display: flex; align-items: center; gap: 12px`,
     and an `::after` that is `flex: 1; height: 1px; background: var(--line-strong)`.
     Level three: `font-weight: 400`, `color: var(--fg-body)`, and
     `background: var(--line-faint)` on the rule.
   - `rule` is the dashed repeating gradient the checkpoint separator used —
     lift it from `git show 58a2c44:src/renderer/src/components/thread/Checkpoint.svelte`.
   - Render a bold segment as `<strong>`; keep the existing `<code>` path.
   - Render an item's `children` as a nested list inside its `<li>`.
6. The nav model must not change here. A heading and a rule stay part of the
   message block they are in; only fenced code splits, and that is I2.

Acceptance: paste the metrics-service README into a thread. Headings render
bold with a rule and at body size; `---` renders as a dashed separator;
`**Admin > Metrics**` renders bold; the four-step list counts 1, 2, 3, 4 with
Name/Unit/Formula nested under step 3; no `#`, `-`, or `*` appears as
punctuation the reader did not write.

Validation: `markdown.test.ts` for each new rule, the nesting, and the inline
state machine; a case asserting `####` clamps to level 3; a case asserting a
line of `---` inside a fenced block stays literal; `pnpm check`; a visual pass
against the mockup.

## I2 — a fenced block is its own stop — `done`

Delivered behavior: `j` through a message that contains code stops at the text
above it, then at the code, then at the text below.

Steps:

1. `src/renderer/src/lib/blocks.ts` — a message contributes one nav entry per
   *segment*, where a segment is either a run of consecutive non-code nodes or
   a single code node:
   - Add `segment?: number` to `NavBlock`, alongside `rowId`.
   - Id is `${blockId}#${segment}`, using `#` rather than `:` so it cannot be
     confused with a ledger row id — block ids already contain `:`
     (`user:e1`), which is why the row separator could not be reused here.
   - A message with no fenced block produces exactly one entry, with no
     `segment`, so nothing about today's ids changes for the common case.
   - `text` for a code segment is the code; for a text segment, its source.
2. New `src/renderer/src/lib/markdown-segments.ts` — `segmentsOf(nodes:
   MarkdownNode[]): MarkdownNode[][]`, the grouping rule above, pure and
   shared by `blocks.ts` and `Message.svelte` so the two cannot disagree about
   what a segment is. This is the whole risk of the ticket: if the renderer
   and the nav model disagree, `j` points at a block that is not drawn.
3. `src/renderer/src/components/thread/Message.svelte`:
   - Take `blockId` and `focusedNav` props, as `Ledger.svelte` already does.
   - Render one wrapper per segment carrying `use:navTarget` and the dim class,
     the same shape the ledger uses for its rows.
   - The streaming caret belongs to the last segment.
4. `src/renderer/src/components/thread/ThreadView.svelte` — pass the props; the
   message's own wrapper stops carrying the nav id when the message has more
   than one segment, or the ring would have two elements claiming it.

Acceptance: a message of text, one fenced block, then text is three stops for
`j`. `a` on the code segment offers `copy text` and copies the code, not the
prose. A message with no code is still one stop. Leap into a word inside the
code lands on the code segment.

Validation: `blocks.test.ts` for the segment ids and the single-segment case;
`markdown-segments.test.ts` for the grouping; a key-path test in
`block-keys.test.ts` walking text → code → text; a real-app pass.

Blocked by: I1

## I3 — code reads as code — `done`

Delivered behavior: a fenced block is syntax-highlighted, and a block still
streaming highlights the line being written without re-reading the ones above.

Steps:

1. New `src/renderer/src/lib/highlight.ts` — pure, no dependency:
   - `export type TokenKind = 'plain' | 'keyword' | 'string' | 'comment' | 'number' | 'punct' | 'name'`
   - `export interface Token { text: string; kind: TokenKind }`
   - `export interface LineState { inBlockComment: boolean; inString: '"' | "'" | '`' | null }`
   - `export function highlightLine(line: string, lang: string, from: LineState):
     { tokens: Token[]; to: LineState }`
   - One scanner, table-driven by language: keyword set, comment markers, string
     delimiters. Cover what agents actually write — `ts`/`js`/`tsx`/`json`,
     `bash`/`sh`, `python`, `css`, `html`, `diff`, and a plain fallback for
     anything unknown. An unknown language must render as plain text, never as
     a guess.
   - No regex backtracking on untrusted input: a single left-to-right pass with
     an index, so a pathological line cannot hang the renderer.
2. `Message.svelte` — render the fence line by line, keyed by index, each line
   `$derived` from its own text and the previous line's end state. That is what
   makes streaming cheap: only the last line's tokens are recomputed.
3. Colours turn with the workspace rather than sitting fixed. `tokens.css`
   gains a triad rotated off `--accent-hue`: `--tone-1` is the accent itself,
   `--tone-2` is +60, `--tone-3` is +180, with chroma falling as the hue
   travels so the accent keeps the loudest voice. Keywords take tone 1 —
   they are the structure, and the accent is the workspace's identity —
   strings tone 2, numbers tone 3. Comments carry no hue at all: they are the
   part the reader skips. Fixed hex would have stopped agreeing with the
   accent the moment a workspace was seeded a different colour.
4. Leave `ToolBody.svelte` alone. Tool bodies already have their own line
   shapes and their own tests; reusing the highlighter there is a later,
   separate change and would double this ticket's surface.

Acceptance: a fenced `ts` block shows keywords, strings and comments in
distinct colours; a `bash` block highlights differently from a `ts` one; a
block tagged with a language nobody supports renders as plain text with no
error; a block streaming in does not flicker or re-colour the lines above the
one being written.

Validation: `highlight.test.ts` per language, including an unterminated string
carrying into the next line and a block comment spanning three lines; a
perf check that re-tokenising the last line of a 500-line block does not
re-tokenise the block; `pnpm check`; a visual pass.

Blocked by: I2

## Order
