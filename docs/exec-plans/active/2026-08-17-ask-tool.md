# Exec Plan: the ask tool

Spec: [2026-08-15-ask-tool.md](../../specs/2026-08-15-ask-tool.md) (approved
2026-08-17).

Status legend: `todo` · `in-progress` · `done`.

## L1 — The widened vocabulary — `done`

> Nothing is visible here, and everything else stands on it. It goes first
> because the change is breaking: `AskOption` is `{ label }` today and one `ask`
> event carries one question, so the reducer, the demo catalog and the card all
> move together or the browser harness starts lying.

- Delivered behavior: `src/shared/vocabulary.ts` carries `AskQuestion` — an
  `id`, a `kind` of `one | many | text`, a prompt, optional `description`, an
  optional `optional: true`, and for the choice kinds a list of
  `AskChoice { id, title, description? }` plus an optional `allowOther` flag.
  `AskAnswer` carries `id`, `kind`, `chosen: string[]`, `labels: string[]`,
  `text?`, `skipped?`. The `ask` event carries `questions: AskQuestion[]`;
  `ask-answered` carries `answers: AskAnswer[]` and an `outcome` of
  `answered | cancelled | ended`. `answerAsk` takes answers rather than an
  option index.
- The reducer's `isPendingGate` keeps working unchanged in meaning: an `ask`
  block with no answers is a pending gate, so `waiting-input` still outranks a
  running turn.
- Acceptance: the demo catalog renders a multi-question ask in the browser
  harness; a thread with an unanswered ask reports `waiting-input`; an answered
  one does not.
- Validation: reducer tests over each kind, the answered record, and each
  outcome. `pnpm check`, and the harness opened once.
- Blocked by: nothing.

## L2 — The tool, blocking on a real answer — `done`

> The backend half, demoable without a single new pixel: call the tool from a
> live agent, watch the `ask` event arrive, answer it with `answerAsk` from the
> devtools console, watch the agent carry on.

- Delivered behavior: `ask_user` is registered in the inline extension beside
  the approval gate, with the description from the spec. `execute` publishes the
  questions as an `ask` event and returns a promise that resolves when
  `answerAsk` arrives, with the JSON result the spec defines — ids and labels,
  `other` plus text for an off-menu answer, `skipped: true` for a skipped one.
  Malformed calls from the model (no questions, a choice question with no
  choices, duplicate ids) resolve immediately with a result that says what was
  wrong rather than throwing.
- A registry of pending asks keyed by tool call id, in the shape the approval
  gate's already uses, so both are released the same way.
- Acceptance: a live agent asking a question blocks; answering releases it with
  the right JSON; the answer reaches the model.
- Validation: a main-side test that `execute` blocks and resolves; one live pass
  under `PIOCARINA_PI_LIVE=1`.
- Blocked by: L1.

> **Proven live.** A real agent, given only the description, called `ask_user`
> with a `text` question, held the turn open until `answerAsk` arrived, and then
> wrote the file using the word it was told. Two facts about pi 0.84 that the
> spec had not recorded and the types did: `parameters` is a **TypeBox** schema,
> not a JSON literal, and `execute` returns content blocks rather than a string.
> `typebox` is pinned to 1.3.7, the version pi itself resolves.

## L3 — The card, and the stepper — `done`

- Delivered behavior: `AskCard.svelte` renders one question at a time with a
  `2 / 3` position, choices as title plus lighter subtext, answered steps
  readable above the current one. `many` shows what is toggled; `text` shows a
  field; a choice question with `allowOther` shows the free-text option and, when
  chosen, its field. The last confirmation submits every answer in one
  `answerAsk`. Once answered the card reads as a finished tool call with a
  summary of the answers under it, and takes no keys.
- Acceptance: three questions of three kinds can be walked and submitted; the
  submitted payload matches what the card showed; an answered card is inert.
- Validation: headless tests over the card's state module; a visual pass in the
  browser harness against §05.
- Blocked by: L1.

## L4 — The keys — `done`

> The rule that makes it feel like this app rather than a web form.

- Delivered behavior: a focused column with a pending question gives `j`/`k` to
  its choices, first choice focused on arrival. `esc` releases them to the
  blocks with the question still pending; `enter` from NORMAL takes them back;
  moving to the asking column with `h`/`l` focuses its card. `space` toggles a
  `many` choice, `enter` confirms a step, `⇧tab` steps back, `o` chooses the
  free-text option and takes the caret. Routing sits in the shell's existing
  modal ranking — below `confirm` and the overlays, above ordinary column keys.
  Nothing takes the caret while the composer has it.
- Acceptance: with a question pending, `j` moves a choice and not a block; after
  `esc`, `j` moves a block again; `enter` returns to the card; INSERT is never
  interrupted.
- Validation: headless key tests through the shell reducer, including the
  ranking against `confirm` and the overlays.
- Blocked by: L3.

## L5 — Being told about it — `done`

- Delivered behavior: a question arriving is revealed in its column when the
  reader is at the bottom of it; when they are scrolled up, nothing moves and a
  sticky bar at the column's bottom edge says a question is below. An unfocused
  column marks its header with a glyph beside the amber dot it already gets. A
  toast is raised carrying the existing `view` jump, on the long lifetime, and
  it expires. A workspace that is not focused marks its rail entry, and never
  switches by itself.
- Acceptance: a question in an unfocused column moves no view; the toast's
  `view` lands on the asking thread; the rail mark clears when the question is
  answered.
- Validation: headless tests over the reveal decision and the toast; one live
  pass with two columns.
- Blocked by: L3.

## L6 — Every way a question ends without an answer — `done`

> The ticket that decides whether a blocked agent is a bug or a state.

- Delivered behavior: sending a message while a question is pending resolves the
  call as cancelled carrying what was said, and delivers the text as an ordinary
  message; the card records *answered in the composer*. Cancelling the turn
  releases the call through `signal` with `turn cancelled`; closing the column
  releases it with `thread closed`. Quitting aborts it with the turn, and on
  reopen the card renders from history as *unanswered — the turn ended* and
  takes no keys. Every path resolves; none throws.
- Two calls in one turn do not stack: the oldest unanswered card holds the keys
  and the other waits.
- Acceptance: each of the four endings leaves a readable record and a released
  tool call; a restarted app never offers an old question to answer.
- Validation: main-side tests for each release path; a reducer test for each
  record; one live pass cancelling a turn mid-question.
- Blocked by: L2, L4.

## L7 — The description, tuned against real use — `done`

- Delivered behavior: a live session across a handful of real tasks, recording
  when the agent asked and whether the question was worth the interruption. The
  description is adjusted from what that shows, and what changed is written into
  the spec.
- Acceptance: recorded in this plan, with the before and after wording.
- Validation: the pass itself.
- Blocked by: L6.

> **What the pass showed, and what changed.**
>
> Three standing probes now live in `pi-live-ask-discipline.test.ts`: one
> question the model should ask, and two it should not. The two it should not
> passed from the first attempt and never regressed — the "do not ask what the
> repository can answer" half of the description was never the problem.
>
> The one it should ask failed twice. First wording: a description that led with
> when *not* to call. The model wrote a careful reply weighing in-memory against
> on-disk and **ended its turn with the question in prose** — which in this app
> means the thread goes quiet and nobody is told anyone is waiting. Rewording the
> description to lead with when to ask did not fix it; the description is read
> when a model is already reaching for a tool, and this model was not reaching.
>
> What fixed it was `promptGuidelines`, which pi appends to the system prompt
> while the tool is active:
>
> > Never end a reply with a question. If you are about to ask the user anything
> > — which approach, what to call it, whether a tradeoff is acceptable — call
> > ask_user instead. A question in prose ends the turn and nobody is told you
> > are waiting.
>
> A softer first draft of the same guideline ("when a decision is the user's to
> make, call ask_user rather than asking in your reply") was not enough. The
> imperative was.
>
> One consequence worth naming: the agent now asks more than once in a turn when
> a task holds two decisions, which is correct and which broke the L2 live test —
> it answered the first question and then waited for a turn that was waiting on
> the second. That test now answers every gate it meets rather than the first.
