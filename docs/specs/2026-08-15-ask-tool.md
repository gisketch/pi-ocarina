# Spec: Ask Tool

Status: **NEED GRILLING** — not approved. The open questions at the end must be
answered with `$sonata-grill` before anyone implements this. Everything above
them is groundwork, not a settled contract.

Visual truth: `PiOcarina Components.dc.html` §05 (ask card) — already built and
rendering from the demo catalog. Behavior truth: this file, once approved.

## Problem & Outcome

The design has an ask card. The thread spec describes it. The reducer builds it
and the renderer draws it. Nothing produces it, because **pi 0.84 has no
elicitation of its own** — no event asks the user anything.

So the ask is ours to build. Outcome: the agent can stop and ask a real
question, the user answers in the thread, and the answer goes back to the model
as the tool's result.

## What pi gives us

Verified against `@earendil-works/pi-coding-agent@0.84.2`:

- `pi.registerTool(definition)` registers a custom tool from an extension. This
  is the same inline-extension mechanism the approval gate already uses, so the
  wiring and its `await loader.reload()` requirement are known.
- `ToolDefinition.execute(toolCallId, params, signal, onUpdate, ctx)` returns a
  promise. It can therefore block until a person answers, exactly as the
  approval gate blocks on `tool_call`.
- `signal` is an `AbortSignal`, so a cancelled turn can release a waiting ask.
- `onUpdate` streams partial results, if a question ever needs to report
  progress.

Nothing here is speculative. The mechanism exists; what it should *do* is what
needs grilling.

## In Scope

The `ask` tool definition and its prompt text, the round trip from tool call to
rendered card to answer to tool result, what the model receives back, and what
happens when nobody answers.

## Out of Scope

The card's appearance (thread-ledger spec, built). Approvals (session-backend
spec). The composer (composer-controls spec).

## Groundwork

The event vocabulary already carries `ask`, `ask-answered`, and the `answerAsk`
command; the driver accepts `answerAsk` and does nothing with it. The seam does
not need to change — only to gain a producer.

## Risks

- An ask that nobody answers holds a turn open indefinitely. The approval gate
  has the same shape and releases waiting calls when a thread closes; this must
  do at least as well.
- A model that asks too often is worse than one that guesses. The tool's
  description is load-bearing and belongs in the grill.

## Open questions — GRILL THESE

1. **What does the model get back?** The chosen label, its index, or free text?
   Does the tool support a free-text answer as well as fixed options?
2. **Is a reply in the composer an answer?** The thread-ledger spec already
   promises "reply via composer also resolves the card". Does any message while
   an ask is pending answer it, or only an explicit action?
3. **What if nobody answers?** Block forever, time out, or auto-cancel the turn?
   What does the model see in each case?
4. **What happens on quit with an ask pending?** The turn is mid-flight and the
   transcript will record something. What?
5. **Is the tool always registered**, or opt-in per workspace? A user who never
   wants to be asked should be able to say so.
6. **Multi-select and default answers** — does the design's single-select card
   cover every case worth supporting in v1?
7. **Does an ask count as a gated action?** It does not touch the disk, so
   probably not — confirm.
