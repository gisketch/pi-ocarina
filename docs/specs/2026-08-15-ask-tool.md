# Spec: the ask tool

Status: **APPROVED.** Grilled 2026-08-17. Ready for tickets.

Visual truth: `PiOcarina Components.dc.html` §05 (ask card), already built and
rendering from the demo catalog — single question, single choice. This spec
widens it. Behavior truth: this file.

## Problem and outcome

The design has an ask card. The thread spec describes it. The reducer builds it
and the renderer draws it. Nothing produces it, because **pi 0.84 has no
elicitation of its own** — no event asks the user anything, so an agent that
needs a decision either guesses or stops and says "let me know".

Outcome: the agent can stop and ask a real question — several, in one
interruption — the reader answers in the thread without leaving the keyboard,
and the answers go back to the model as the tool's result.

## What pi gives us

Verified against `@earendil-works/pi-coding-agent@0.84.2`:

- `pi.registerTool(definition)` registers a custom tool from an extension — the
  same inline-extension mechanism the approval gate already uses in
  `session-factory.ts`, including its `await loader.reload()` requirement.
- `ToolDefinition.execute(toolCallId, params, signal, onUpdate, ctx)` returns a
  promise, so a call can block until a person answers, exactly as the approval
  gate blocks on `tool_call`.
- `signal` is an `AbortSignal`, so a cancelled turn releases a waiting ask.

## In scope

The `ask_user` tool and its description; the round trip from tool call to card
to answer to tool result; the stepper and its keys; what the reader sees when a
question arrives while they are elsewhere; every way a question can end without
being answered.

## Out of scope

Approvals (session-backend spec). The composer itself (composer-controls spec).
Any question kind beyond the three below — the shape is built to take more, but
v1 ships three.

## Settled decisions

1. **Always registered.** The tool is part of what PiOcarina is, not a setting.
   Every session in the app gets it.
2. **The name is `ask_user`.** A verb and its object. Not gated by the approval
   flow: it writes nothing, reads nothing, reaches nothing — it *is* a prompt,
   and a dialog in front of a dialog is absurd.
3. **The description says when to ask and when not to, and a prompt guideline
   makes the model reach for it at all.** Amended after L7's live pass: a
   description alone left the model writing its question into its reply and
   ending the turn, which in this app means nobody is told anyone is waiting.
   pi's `promptGuidelines` carry the imperative — never end a reply with a
   question; call `ask_user` instead. The description itself says both halves:
   ask when the answer changes what happens next and cannot be found in the
   repository; do not ask what the code answers, do not ask permission for work
   already agreed, do not report progress; and carry several questions in one
   call rather than a run of them. Both are strings, and both are the easiest
   thing here to tune after living with it.
4. **One call can carry several questions**, walked as a stepper in one card. A
   three-part decision is one interruption, not three.
5. **Three kinds of question:** `one` (pick one), `many` (pick several), `text`
   (free text). A choice question may also offer a free-text option, chosen and
   typed **in the card** — never in the composer.
6. **A choice is an id, a title and an optional description.** The description
   renders as lighter subtext under the title, which is what lets a real choice
   be readable without a paragraph in the question.
7. **Built to be extended.** The tool takes a list of questions, each with a
   `kind`, so a new kind is a new `kind` value and a renderer for it — not a new
   tool and not a new seam.
8. **The model gets ids and labels back**, keyed by each question's own id:

   ```json
   { "answers": [
     { "id": "scope", "kind": "one",  "chosen": ["worktree"], "labels": ["Its own worktree"] },
     { "id": "hosts", "kind": "many", "chosen": ["gh", "gl"], "labels": ["GitHub", "GitLab"] },
     { "id": "name",  "kind": "text", "text": "fix/OCA-231" }
   ] }
   ```

   Ids are what a model branches on; labels stop it having to remember what an
   id meant. A free-text answer to a choice question carries the `other` id and
   the text together, so the shape says both that the reader went off-menu and
   what they said. A skipped question comes back with `"skipped": true` rather
   than being absent: a missing key reads as a bug, and "no preference" is not
   "never asked".
9. **A question that arrives is revealed** in its column, through the same
   reveal the transcript already uses, so it comes into view with the label
   above it rather than alone.
10. **How far the interruption reaches**, by where the reader is standing:

    | reader is | what happens |
    |---|---|
    | in that column, at the bottom | the question is revealed |
    | in that column, scrolled up | nothing moves; a sticky bar at the column's bottom edge says a question is below |
    | another column, same workspace | no view change; header mark, and a toast |
    | another workspace | toast with its `view` jump, and a mark on the rail entry; the workspace never switches by itself |
    | typing in INSERT | nothing takes the caret, ever |

11. **The toast expires like every other toast.** It notifies; it is not the
    record. The header and the transcript hold a pending question, and those do
    not time out. It takes the long lifetime, because it asks the reader to
    decide whether to go there.
12. **The column says it is waiting**, with a glyph in the header and not only a
    colour. The state exists already: a pending ask makes the reducer report
    `waiting-input`.
13. **A pending question owns `j` and `k` in its column. There is no jump key.**
    The choices take focus when the card arrives, first choice focused, so
    nothing has to be reached for.
    - `esc` gives the column back: `j`/`k` return to blocks, the question stays
      pending, and the card shows it is no longer holding the keys.
    - `enter` from NORMAL takes them again. It is unbound there today, and it is
      the key the card answers with.
    - Moving to the asking column with `h`/`l` focuses its card the same way.
      One rule: a focused column with a pending question, not released by `esc`,
      has the choice keys.
    - In the card: `j`/`k` move, `space` toggles a `many` choice, `enter`
      confirms the step and advances, `⇧tab` steps back, `o` chooses the
      free-text option and puts the caret in its field.
    - The last `enter` submits every answer at once. A model handed answer one
      while the reader is still on question two is acting on half a decision.
    - No number keys for options — `1`–`3` are the workspaces. No `y`/`n`
      shortcut — this is not a confirm dialog.
14. **Prose instead of a choice cancels the question.** The composer is never
    disabled. Sending while a question is pending resolves the call as cancelled
    carrying what was said, and delivers the same text as an ordinary message.
    The card becomes a record reading *answered in the composer*, showing the
    message that replaced it.
15. **After the answer the card is a record**: the row reads as a finished tool
    call — the questions that were asked — with a summary of what was answered
    under it.
16. **A question waits as long as its thread does. No timeout.** A timeout fires
    while the reader is at lunch and hands the model a "no answer" it will act
    on. The honest cost is that a blocked turn can be parked overnight, and five
    asking threads park five turns; the headers are what make that visible.
17. **Three things release a waiting question**, each resolving the call rather
    than throwing — a tool that throws teaches a model to ask again:
    - cancelling the turn, via `signal`, reason `turn cancelled`;
    - closing the column, reason `thread closed`, which is what the approval
      gate already does for waiting calls;
    - quitting, which aborts the call with the turn. On reopen the card renders
      from history as *unanswered — the turn ended*, and is not re-askable: the
      call it belonged to is gone.

18. **A question may be marked `optional`.** Added during L1 and recorded here
    rather than left as undeclared surface: a caller that genuinely does not
    need an answer can say so, and the reader may step past it. It is the only
    way a question can be skipped, and a skipped question still comes back with
    `"skipped": true` rather than being absent.
19. **The toast has a tone of its own.** It takes the long lifetime because it
    asks the reader to decide whether to go somewhere; borrowing the error tone
    to borrow its lifetime would draw a question in the colour of a failure.

## Acceptance behavior

- An agent calls `ask_user` with three questions; one card appears, showing
  `1 / 3`, with the first choice focused and `j`/`k` moving between choices.
- Answering all three sends one result carrying every answer, keyed by question
  id, with ids and labels.
- A `many` question returns every chosen id; a `text` question returns text; a
  choice question answered off-menu returns `other` and the text.
- The card, once answered, reads as a finished tool call with a summary of the
  answers, and no longer takes keys.
- `esc` releases the keys with the question still pending; `enter` takes them
  back; the column header says it is waiting throughout.
- A question arriving in an unfocused column moves nothing, marks the header,
  and raises a toast whose `view` goes to that thread.
- Sending a message while a question is pending resolves it as cancelled and
  the message arrives as an ordinary user message.
- Cancelling the turn, and closing the column, each release the call with their
  own reason; neither throws.
- After a restart, an unanswered question renders as a record of a turn that
  ended, and cannot be answered.

## Implementation constraints

- The tool is registered in the existing inline extension beside the approval
  gate, and needs the same `await loader.reload()`.
- `src/shared/` is the only seam. `AskOption` today is `{ label }`; it becomes a
  choice with `id`, `title` and optional `description`, and the `ask` event
  carries a list of questions rather than one. `answerAsk` carries answers, not
  an option index. Both are breaking changes to the vocabulary, and the demo
  catalog and reducer tests move with them.
- The renderer never learns what pi is: the card reads events and sends
  `answerAsk`, as it does today.
- The card lives inside a column, which carries `content-visibility: auto` and
  therefore paint containment. Anything that must escape the column's box —
  it should not need to — belongs in a floating surface instead.
- Key routing goes through the shell's existing modal ranking, below `confirm`
  and the overlays, above ordinary column keys.

## Validation

- Reducer tests over the widened vocabulary: several questions, each kind, the
  answered record, and the three release paths.
- Headless tests for the key grammar: focus on arrival, `esc` release, `enter`
  re-entry, stepping, submitting once at the end.
- A main-side test that a registered `ask_user` call blocks until answered and
  resolves with the answers — the approval gate's test shape.
- One live pass under `PIOCARINA_PI_LIVE=1`: a real agent calls the tool and
  acts on what it gets back.

## Risks

- **The description is the whole product.** Too eager and the reader stops
  reading cards; too discouraging and the model guesses instead of asking. It
  will need tuning against real use, and that is expected rather than a defect.
- **A blocked turn is invisible from another workspace** once its toast has
  faded. The rail mark is the only carrier; if that proves too quiet, the
  workspace switcher is the next place to say it.
- **Widening `AskOption` breaks the demo catalog**, which is what the browser
  harness renders. Both move together or the harness lies.
- **Two pending questions in one thread** cannot happen through one call, but
  two calls in one turn could produce it. The card that has the keys is the
  oldest unanswered one; the other waits its turn rather than stacking.
